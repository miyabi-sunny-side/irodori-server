# 構成

irodori-server は Rust (axum) のサーバーと Svelte 5 の画面、推論を担う Python のプロセスでできています。

```text
ブラウザ ── HTTP ── irodori-server (Rust)
                     ├─ data/irodori.sqlite3    生成の記録・参照音声・読み辞書
                     ├─ data/audio/*.wav        生成した音声
                     ├─ data/references/*       アップロードした参照音声
                     └─ 子プロセス: .venv/bin/python irodori_worker.py
                                    └─ Irodori-TTS (固定 revision) の _run_generation
```

## 推論プロセス

サーバーは起動時に `irodori_worker.py` を子プロセスとして起動し、所有します。
モデルは推論プロセスの中に常駐し、2 回目以降の生成は読み込みを省きます。

- 通信は標準入出力の JSON Lines です。1 行の要求に 1 行の応答を返します。
  生成は 1 件ずつ順に処理するため、要求と応答の対応付けが要りません。
  同じマシンの親子間で完結し、ポートやソケットファイルを増やさずに済むことが選んだ理由です。
- upstream は標準出力へログを書くため、推論プロセスは標準出力を標準エラーへ付け替え、
  複製した元の標準出力だけを応答に使います。ログはサーバーのログにそのまま流れます。
- 推論プロセスが終了していたら、サーバーは次の要求の前に起動し直します。
  応答の途中で終了した要求は失敗として返します。
- 推論プロセスは `_run_generation` を呼んで WAV を渡されたディレクトリへ書くだけです。
  SQLite と `data/audio` へ書くのはサーバーだけです。
- ブラウザを閉じても生成は最後まで進み、記録されます。

## 記録とファイルの整合

生成では、推論プロセスが `data/tmp/<batch>/` へ書いた WAV を一時名のまま仕上げます。
話速を変える場合は ffmpeg の `atempo` で一時ファイルに書き出します。
仕上がった WAV を `data/audio/<batch>_<候補番号>.wav` へ移し、その後に全候補の記録を 1 つのトランザクションで確定します。
記録に失敗したら移したファイルを消します。`data/tmp/<batch>/` は成否にかかわらず消します。

削除では、先に記録を消してからファイルを消します。
ファイルを消せなかった場合は `file_errors` に残し、履歴の画面に表示します。

## 読み辞書

読み辞書は SQLite の `dictionary` テーブルにあります。
データベースを新しく作るときだけ、Gradio 版の `config/reading_dictionary.json` を取り込みます。
元の JSON は変更・削除しません。取り込んだ後に辞書を空にしても、再び取り込むことはありません。

## 公開範囲

家庭内 LAN での利用 (level-1) を前提とし、認証はありません。アプリは次を守ります。

- 外部コマンド (ffmpeg) は引数の配列で呼び、shell を通しません。
- 保存するファイル名はサーバーが決めます。アップロード時のファイル名は表示にだけ使います。
- 参照音声は拡張子を限定し、50MB までにします。
- SQL はすべてパラメーターで渡します。

LoRA フォルダの指定は Gradio 版と同じく推論プロセスへそのまま渡します。
LAN 内の利用者を信頼する前提による判断で、公開範囲を広げるときに見直します。
